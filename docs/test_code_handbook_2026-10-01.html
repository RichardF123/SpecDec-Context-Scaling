0.3 三条最常见的误用（先看这里）

  1. 每次 pwsh/命令行调用都是新进程：环境变量不会保留。设置变量与执行命令必须写在同一行

（本项目因此浪费过 1 次 GPU 运行）。

  1. 摘要一致 ≠ 逐位一致：sha16 只能叫"摘要一致"；要逐位就必须 torch.equal（逐张量/逐元素）。
  2. 后续 token 相同 ≠ 缓存状态相同：两臂可以生成完全相同的 token 序列而 KV 缓存已经不同（本项目已实测到）。

9. 方法论：这些工具共同的实现方法

9.1 复现门（先复现，再归因）

任何定位前先证明"我能重放出现象"：重放/重跑的结果必须与既有快照逐位相同（k_post、v、

完整 64-token 序列与 gen_hash）。未过门 ⇒ 落盘停止，不用后续差异讨论正确性。

本项目的 C1 定位、L0 定位、AR/Spec 定位都走这条门。

9.2 控制格 vs 干预格（不为没发生过的组合编造参考）

四格里只有 H_AR-S（AR 历史 × 串行）与 H_SP-B（Spec 历史 × 分块）在真实运行里发生过 ⇒

只要求这两格逐元素复现真实捕获行；另外两格是干预，不设参考、不编造参考。

9.3 摘要约定（很容量错的地方）

  • stable_sha：sha256(t.float().cpu().contiguous().numpy().tobytes())[:16] ⇒ 跨进程可比。
  • 只在同一工具、同一约定内用 sha 判等。例：smoke 工具哈希的是整块 (1,2048,V) 输出，

而 c1rope 哈希的是末位 (V,) 行 ⇒ 两者 sha 本来就不该相等，直接比会得出错误结论（本项目踩过）。

  • 跨设备：GPU 上求的 sum 与 CPU 上重算的 sum 会因归约顺序差 1 个 fp32 ULP ⇒ 只用

argmax/max/margin 这类与归约顺序无关的量做跨工具对位。

  • 逐张量 torch.equal 强于摘要；能在同一进程里比就比逐位。

9.4 泄漏检查必须带阳性对照

CELLS_LEAK_CHECK：把决策行之后的尾槽 token 换掉 ⇒ 决策行必须逐位不变（无泄漏）；

同时要求被替换的尾槽自身的行确实改变（阳性对照）。没有阳性对照的"没变化"是空证据。

9.5 四格与归因规则

同一历史换形态 ⇒ 支持"执行形状影响"；同一形态换历史 ⇒ 支持"缓存历史影响"；

两者并存或依赖历史时如实报告交互，不强行选唯一原因。

margin 大小不能单独判定逻辑错误或数值误差（本项目的 classify_bf16_compare 还额外要求 fp32_margin，

缺证据一律 NEEDS_INSPECTION ⇒ 缺证据不得豁免）。

9.6 快照完整性

缓存快照必须用 cache_clone.clone_list_cache_full（copy.deepcopy）：保留全部层内键

（张量 + 非张量元数据）与长度信息。只复制 K/V 就是 bug（b0db582 修掉的正是这一类：

HF DynamicLayer.is_initialized 丢了 ⇒ 首次 update() 清空历史）。

9.7 lineage 纪律

跨谱系（A/B）不混比；新产物必须写明 target_rope / rope_inv_freq_source；历史产物原样保留。

9.8 失败保留与不覆盖

  • 新产物全部带 run_id/时间戳；绝不覆盖历史文件；比较类工具输出名带写入时间戳。
  • 失败记录（崩溃 JSON/日志、注入故障自测、被撤回的结论）一律保留，原文加标记而不删除。
  • 每次改动都在产物里写清"来源/口径/强度"，让后来者能判断"这条数字能不能用"。

9.9 进程与环境模型

  • 每次命令行调用是新进程：环境变量不保留 ⇒ 变量与命令写在同一行。
  • 诊断与真实运行分进程、GPU 串行（绝不双模型以外并发）；每个真实运行独立 commit_guard + P-state 预检。
  • 计时只作诊断，禁止进入任何 speedup 表；allocated ≠ 物理占用，reserved 超物理容量不单独证明分页。

9.10 陷阱清单（本项目实际踩过的，按"教训"记）

#陷阱后果现在的做法
