# 正确性问题复盘：从 QK 精度到 KV 缓存历史

记录日期：2026-09-29（Asia/Hong_Kong）  
用途：保存这次判断的证据、适用范围和下一步决策逻辑，供后续复盘。  
证据截止：提交 `ec42713` 对应的缓存历史探针结果。记录时工作树有执行 agent 正在修改的 finite 汇总相关文件；本文不审定这些尚未完成复核的修改，也不覆盖它们。  
性质：分析备忘，不是新实验结果、协议修订或正式实验放行。

## 1. 当时究竟卡在哪里

模型前向、KV cache、V-only FP8、固定链 SpecDec 均已实现。CPU FP32 B6 有 20/20 的实现正确性证据，缓存长度、验证索引及 EOS 分支也有专门测试。

但在当前 8K、GPU BF16、`cudnn_prefill` 配置下，AR 与 SpecDec 对同一输入的完整生成 token IDs 不总是相同。这个问题不能被“程序能跑完”“没有 NaN”“结构检查通过”替代回答。

需要分开看三个层面：

| 层面 | 要回答的问题 | 当前证据与边界 |
|---|---|---|
| 算法和结构 | 候选验证、接受、拒绝、缓存回滚是否按设计执行？ | 已有结构、索引、EOS 和高精度测试；本次未发现新的引擎逻辑错误 |
| 生产数值路径 | 当前 backend/dtype 下，是否逐 token 复现指定 AR 实现？ | 本批 8K 样本仍有分歧，不能记为完整一致 |
| 研究验收 | 哪些差异可接受、用什么参照、何时能做正式实验？ | 必须依据明确且经批准的协议；局部归因成功不自动放行 |

“数学算法等价”和“有限精度执行结果逐位一致”不是同一个命题。FP32 测试通过不证明所有 BF16 路径完全一致；BF16 发生分歧也不能直接证明算法写错。

## 2. 证据链是怎样逐步建立的

### 2.1 原始现象：第 32 个生成 token 分叉

配置：target 1.5B、draft 0.5B、ctx=8192、chunk=2048、max_new=64、k=4、greedy；prefill 使用 cuDNN，其他相关阶段仍 eager。

| KV 档位 | 共同前缀 | 生成 index31 的 AR token | Spec token |
|---|---:|---:|---:|
| base_bf16 | 31/64 | 1083 | 5880 |
| v_fp8 | 31/64 | 5880 | 1083 |

index 从 0 开始，因此 index31 是第 32 个生成 token。共同前缀长度不是 token 总一致率，更不是语言准确率。

### 2.2 先修诊断，再相信诊断

早期 2×2 工具曾把生成预算从 64 改成 32，导致目标轮只剩 2 个候选预算，实际验证 Kp=2，却拿 Kp=4 的重放作比较。另一个问题是浅拷贝缓存字典仍共享张量，不能有效检测原地修改。

修订版恢复 max_new=64/k=4，用 hook 捕获后停止；使用独立缓存副本和完整 logits 比较。两档真实目标行与同条件重放逐元素相等，max|Δ|=0。

这一步建立的是“分歧被忠实复现”，不是“分歧已修复”。在固定缓存下，single 与 block 计算有数值差异；不同真实历史建立的缓存也有数值差异。

证据 tag：`div2x2v2b_20260928T004000Z`；对应提交 `7c00bd6`。

### 2.3 QK FP32 干预：有效，但不足够

测试只提高 target eager 路径中的 QK 矩阵乘法及缩放精度。draft 保持原精度；融合 prefill 绕过该开关；权重、缓存和最终 logits 没有整体切换为 FP32。

控制组四条 64-token 序列完全复现旧实验，因此可以有依据地比较干预后的变化。

| KV 档位 | 控制组共同前缀 | QK FP32 后共同前缀 | 判读 |
|---|---:|---:|---|
| base_bf16 | 31/64 | 52/64 | 分歧推迟，不是 PASS |
| v_fp8 | 31/64 | 58/64 | 分歧推迟，不是 PASS |

原 index31 上，两档干预后均为 AR=Spec=5880。但 AR 参考自身也发生变化，所以不能写成“原参考输出被原样恢复”，不能由更长共同前缀推断语言质量提高。

证据 tag：`qk32c_20260928T025500Z`；对应提交 `45817a5`。

### 2.4 新分歧的关键特征：两边当前都是单步计算

base_bf16 的新分歧位于生成 index52，即第 53 个生成 token。AR 的决策来自单步 decode；Spec 的决策来自上一轮 target repair 的单 token 前向。

这意味着不能再简单解释为“当前 AR 算 1 个、当前 Spec 算 4 个”。需要问：即使当前计算形状相同，之前留下的缓存差异是否足以改变决策？

## 3. 缓存历史单变量对照具体证明了什么

固定当前 token、位置、入口与精度，只替换真实缓存历史：

| 控制量 | AR 侧 | Spec 侧 |
|---|---|---|
| 当前输入 token | 323（生成序列 gen[51]） | 323 |
| 输入绝对位置 | 8243 | 8243 |
| 输入前 cache 长度 | 8243 | 8243 |
| 预测绝对位置 | 8244 | 8244 |
| 预测生成 index | 52 | 52 |
| 重放前向入口 | spec_dec._step | spec_dec._step |
| 精度 | target-only QK FP32 | target-only QK FP32 |

位置核算：8192 个 prompt token 加上前 51 个已写入的生成 token，得到输入前缓存长度 8243；当前送入第 52 个生成 token，即 gen[51]，预测 gen[52]。不能把已经写入当前 token 的缓存再次拿来喂同一 token。

两侧先验证“重放是否等于各自真实行”：逐元素相等，max|Δ|=0；独立快照完整性通过。本次 Spec repair 的前置缓存由独立 block 快照按 pre+m 截断重建，且与 verify 前快照逐张量交叉核对相等；不能把它描述为任意截断后自然正确。

| 结果 | AR 历史缓存 | Spec 历史缓存 |
|---|---:|---:|
| token279 的 logit | 20.750 | 20.750 |
| token64871 的 logit | 20.750 | 20.875 |
| 顶部并列集合 | [279,64871] | [64871] |
| top1-top2 margin | 0 | 0.125 |
| argmax | 279 | 64871 |

两份缓存的最大绝对差为 0.375；两条完整 logits 行的最大绝对差为 0.25。这些是不同张量空间里的绝对差，不是质量损失率，不能互相换算。

**允许的结论：在 base_bf16/index52 的这组受控单步重放中，真实缓存历史的数值差异足以改变该位置的 argmax。**

证据 tag：`reshistc_20260928T154500Z`；对应提交 `ec42713`。

## 4. 当前最有证据的机制解释

可分成两段：

```text
AR 单步推进 / Spec 块验证、裁剪、repair
              ↓
不同历史计算路径产生不同数值缓存
              ↓
同一当前 token + 同一位置 + 同一单步计算
              ↓
不同 logits
              ↓
候选分数接近或并列时，argmax 不同
```

后半段已经有本次局部对照证据。前半段的具体首发机制尚未完整定位：计算形状、矩阵乘法与归约、舍入，以及各层传播都可能参与。不能只凭最终 cache 不相等就判定是哪一层、哪个算子产生了问题。

准确表述是：“复现这一位置的差异，不需要当前这一步的计算形状不同。”不能写成“形状效应已排除”，因为历史 cache 本身仍可能受此前不同计算形状影响。

同样，不能把原因简单归为 cuDNN：本次双方使用相同 backend 策略，当前目标计算为 eager 单步。融合 prefill 的独立正确性与质量验收仍需保留，但本次不证明 cuDNN 算错。

## 5. 为什么几个直觉修法还不足以成立

### 5.1 只提高当前 QK 精度

已有 cache 的数值不会因为后续乘法升精度而自动恢复。其他算子和最终 logits 仍有有限精度效应。QK FP32 的局部改善已经实测，但不是完整一致性的保证。

### 5.2 只把缓存 cast 成 FP32

把已经舍入过的 BF16 值扩成 FP32，只是更精确地表示这个已舍入值，不会恢复早先丢失的信息。重新以另一精度计算整个历史与单纯改变存储 dtype 是两种干预，成本与语义都不同。

### 5.3 改并列选择规则

当前 argmax 规则未被证明错误。表中一边并列、另一边严格领先，因此相同规则也会产生不同结果。规则变更可能碰巧对齐一个样本，却改变其他位置的生成语义。不能称为“修好 tie-break”。

### 5.4 小 margin 时单步重算

本次两侧已经都是单步。若各自仍使用不同历史缓存，重算当前一步不保证恢复指定 AR 轨迹。若需要同步重建历史，则必须明确重建范围、触发规则和成本，不能把这种额外计算从计时中排除。

### 5.5 继续叠加精度开关

分歧位置向后移动不等于一般性正确性改善保证。连续针对同一 prompt 调开关还可能形成样本特化。下一轮应有明确假设、停止条件及独立回归，而不是一直重复直到这条 prompt 恰好 64/64。

## 6. 还需单独收尾的测试工具问题

第一次 finite 汇总错误：AR 没有 draft，却要求 target/draft 都通过，导致 AR 被误写 false。后续已经产生保留原始 JSON 的修订分析。

但在 `ec42713` 版本，又发现反方向的边界漏洞：仅对 executed 模型取合取，会漏掉 required=True、executed=False 的检查。已用 CPU 构造 target 正常、draft 必需但未执行的反例，汇总仍返回 True。live 入口也不能把应有但缺失的模型记录自动推断为 N/A。

应遵守的合同：

- AR 的必需模型是 target；Spec 是 target 与 draft。
- 必需检查应有记录、已执行且明确通过，否则整体资格失败。
- 只有显式不适用的模型可排除；缺失不等于不适用。
- 空记录不能通过；required 与 N/A 冲突必须被检查。
- 若保留 all_executed_ok 的字面含义，必须另设完整资格字段，调用方不能混用。

本缺陷应以 CPU 测试和旧产物离线复核收尾，不需要重新运行本次 GPU 历史缓存实验。记录时这些文件已有未提交修改，因此此处保存的是已发现问题和期望合同，不宣称最终修复已验收。

## 7. 为什么下一步要转向生产正确性方案决策

本次已经回答一个有限但清晰的问题。继续重复同样的缓存对照，不会自动解决完整生成不一致。下一阶段要回答“我们准备交付什么保证，如何达到并验收这个保证”。

### 7.1 先明确保证与参考对象

需要确认：算法结构正确性、高精度实现正确性、生产 BF16 对指定 AR 的 exact-token 一致性分别承担什么角色。现行 G5 中的 FP32 主门与 BF16 near-tie 分类、新 backend 的验收提议，要一起审阅，不能片面引用其中一个门就宣称整体通过。

若保持严格 exact-token 要求：候选方案必须解释为什么数值执行与缓存状态足够一致，而不是只承诺提高平均精度。若团队要接受经过量化验证的生产数值差异：这属于需批准、版本化的协议变更，必须补充独立证据，并保留原门未通过的事实。

### 7.2 审查方案，再做一个最小验证

每个方案至少回答：

1. 改的是哪个计算阶段、历史状态还是仅最终决策？
2. 是否改变 AR 参考输出、量化语义或 backend？
3. 提供的是理论保证、有限 case 通过，还是经验改善？
4. 对显存、prefill、decode 和工程复杂度有什么代价？
5. 最小实验、独立回归与停止条件是什么？

不要自动选择全模型 FP32，不要把局部 fallback 当成已保证全局等价，也不要以“小 margin”直接豁免。

### 7.3 正确性方案确定后再验收测量

任何新增重算、fallback 或 cache 同步都要计入性能。不能用修复后正确性配修复前速度拼出结论。最终配置还需覆盖多 prompt、上下文长度、EOS/预算边界、资源与重复测量，并确认最终后端的质量指标。

明确的负加速结果是可接受的研究结果；不明确的正确性合同和不可靠的计时不是。

## 8. 当前判断的边界

| 可写 | 不可写 |
|---|---|
| 本例缓存历史差异足以影响决策 | 所有分歧都只有缓存这一个原因 |
| 当前单步形状相同仍有分歧 | 历史计算形状已经被排除 |
| 本轮未发现新的引擎逻辑错误 | 整个引擎所有路径已彻底证明无 bug |
| QK FP32 使这两个样本共同前缀变长 | 更高质量、全局正确性保证或正式 PASS |
| 分歧点已可靠复现与局部归因 | 完整 64-token 回归已经通过 |
| CPU 汇总反例需要修复 | 本轮已经观察到 GPU NaN |

## 10. 一句话结论与待更新项

**我们已经把“当前一步怎么计算”与“之前留下什么缓存”分开看，并在一个真实分歧点证明了后者足以改变选择；还没有证明其历史首发机制，也没有恢复完整生产输出一致性。下一步应收尾测试合同并明确生产正确性方案，而不是无限移动分歧位置。**

- [ ] finite 汇总修复完成并复核 CPU 回归。
- [ ] 明确生产正确性参考、验收合同与协议批准状态。
- [ ] 选择一个候选方案，预先写最小实验及停止条件。
- [ ] 最终配置通过正确性、质量、资源与测量验收后，决定是否放行正式矩阵。
