## 3. 更正与缺陷（旧产物、旧字段**原样保留**）

### 3.1 确定的日志缺陷：`replay_saved_next_argmax` **恒为 0**（已修 + 已加回归测试）

* **原来是什么**：`spec_history_rebuild.py` 里
  `int(saved_next.reshape(-1)[-1].argmax())`。
  `saved_next` 形状 `(1,1,V)`，`reshape(-1)` 把它压成**一维 V 个元素**，`[-1]` 取到的是
  **最后一个词表的 logit 标量**，再对标量求 `argmax` ⇒ **恒为 0**。
* **实测确认**：旧产物 `divasc_rebuild_20261001T220737Z.json` 的 23 轮该字段**全是 0**（已核对）。
* **改了什么**：抽出 `_row_argmax(lg) = int(lg.reshape(-1, lg.shape[-1])[-1].argmax())`（先取**最后一行**再取词表维 argmax），
  并额外记录 `replay_saved_next_sha`（该行摘要）与 `replay_saved_next_shape`（可事后核对行身份）。
* **原理/输入输出**：输入是该轮重放末步的 logits（`(1,1,V)`），输出是**词表维**上的 argmax（int）与行摘要。
* **影响范围（诚实边界）**：只影响**诊断字段**；`saved_next = lg_last` 的实际赋值**未被影响**，
  生成/判定结果**未被影响**。全仓库检索确认**只有该模块自己**引用过这个字段
  ⇒ **没有任何结论建立在它上面**；旧 JSON 里的那一列**标注作废**，
  由于当时**没有**保存对应的完整 logits，**不**给"修正值"、**不**回填。
* **回归测试（CPU，先过门再用 GPU）**：构造词表 argmax 索引**非 0** 的 logits，断言
  ① 旧写法确实恒为 0（把缺陷钉在测试里）② 新写法取到 37 ③ 多行输入只取**最后一行**；
  另跑一个受控场景（位置 2..39 全部映射到 token 63），断言**每一轮**的
  `replay_saved_next_argmax == 63`。模块 CPU 门：**PASS 29 / FAIL 0**（含新增 7 条）。

## 4. 实验设计（为什么是这四格、锚点是什么）

* **格定义**（沿用四格工具既有布局，**未**新建一套框架）：在同一份快照上
  `S`：依次单步喂 `FEED=[20642]`，取**末位行**（预测 8209）；
  `B`：一次块前向喂 `CANDS=[20642,659,576,4531]`，取 `rows[0]`（同样预测 8209）。
  两条历史 = `H_AR`（串行历史；与重建历史在 `[0,8208)` 上**实测逐位相同**）与 `H_SP`（原 Spec 的块保留历史）。
  每格从**独立完整克隆**开始（`clone_list_cache_full`，保留全部层内键）。
* **为什么用 8208/8209 这一组**：这是上一轮观察到的**新首分歧**现场：
  `pre=8208`、`cands=[20642,659,576,4531]`、`g[1]=rows[0]` 决定位置 8209 的 token；
  `saved_next` 给的是 `g[0]`（= 位置 8208 的 token 20642），**不是**这个分歧槽
  ⇒ 因此**只需要**检查这一行，**不需要**（也**不做**）任何"把新缓存与旧 logits 混搭"的自由生成实验。
* **锚点是什么**：真实**运行记录**里该位置的 argmax ——
  AR：`run.gen[17]`（串行单步产出）；重建/原 Spec：`rounds[pre=8208].g[1]`（块验证 `rows[0]` 的 argmax）。
  锚点是 **argmax 级**；本轮**没有**捕获到这两个位置（8209）的**整行**真实参考
  ⇒ 只能说"复现了 **token 选择**"，**不能**声称"完整 logits 逐位复现现场"。

## 6. 数据流：同一份历史 → 单步/块计算 → 预测 8209 的行 → 323 / 659

```
固定起点 H(8208)  = 位置 0..8207 的 target KV（28 层，bf16）
                    —— 来自落盘快照的**纯切片**（逐张量核对与源前缀逐位相同）
   │
   ├─ S（单步）: H(8208) → `spec_dec._step(20642)`            → 末位行（预测 8209）
   │                └ 该行 logits：323 = 23.75，659 = 23.75 ⇒ **精确并列**（margin 0）
   │                   `argmax` 取最小索引 ⇒ **323**；`topk[0]` 在并列时顺序未定义（列出 659）
   │
   └─ B（块）:  H(8208) → `spec_dec._verify([20642,659,576,4531])` → `rows[0]`（预测 8209）
                    ├ 串行历史 H_AR：659 = 23.75，323 = 23.625 ⇒ **659 领先 1 ULP（0.125）** ⇒ **659**
                    └ 块保留历史 H_SP：659 = 23.75，323 = 23.75 ⇒ **精确并列** ⇒ **323**

真实运行的锚点（argmax 级）：
  AR 运行     （串行历史 + 串行单步）→ 323  ← 与本 run 的 H_AR-S 一致
  重建运行   （串行历史 + 块验证）  → 659  ← 与本 run 的 H_AR-B 一致
  原 Spec 运行（块保留历史 + 块验证）→ 323  ← 与本 run 的 H_SP-B 一致
```

**读法**：位置 8209 的判定在 bf16 上是**贴边**的（三格并列、一格差 1 ULP）。
`argmax` 与 `topk` 在并列时给不同的"第一名"是**报告陷阱**，不是矛盾；
"哪一侧数值更对"需要 fp32 对照，本轮**没有**做，因此**不判定**。
