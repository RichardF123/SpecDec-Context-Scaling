## 4. 结论（明确回答 a/b/c）

**(a) MUST 全范围（v4 字面：L1–L5 + fp8 KV + 2/4/8K 曲线 + 外部基线 + 复现 + K1/K2 双 kernel）能否在预算内完成？**
**不能安全完成。** R 档 ≈ 247h（超预算上沿 ~3–25%），P 档 443h。仅当真实可用时间 ≥240h 且运气偏好时才贴线可行。**不含 K1/K2 的纯 PyTorch MUST（R≈187h）是能完成的**——差距全在 CUDA 轨。

**(b) SHOULD（动态树 / 0.2B 训练头 / int4 KV）能否叠加？**
**现实上不能。** 叠加需再 +80h（R），只有 MUST 提前一周以上全绿才可能做其中**一项**；v4 已把三者与标题解耦是对的，但"90 GPU 分钟训练头"作为成本幻觉要戳破：首次搭训练管线真实 ≥20–30h。

**(c) 单条最高杠杆改动？**
**排序反转 + 把 K2 从 MUST 降为带止损的 SHOULD，并把整条 CUDA 轨当作"尾巴上的加分项"而非主线**：
1. **9 月内做冒烟**（最险风险先退役，提案前有证据）；
2. **10/7–11/14 只做纯 PyTorch MUST 链**，按 W4→W5→W6→W7→W8 顺序，数据 **11/14 冻结**；
3. K1 放 11/11–11/17（时间盒 ≤20h，过不了就 Triton/eager + 诚实留档，不拖主线）；**K2 只在 K1 绿且 11/20 前可完成时才做**，否则报告写成"K2 未达门、以 eager int8 证据替代"——降级链本身就是 v4 承诺的叙事，不丢分；
4. gpt-fast 降为可选（WSL2 或放弃，transformers 基线已够"外部对照"分）；
5. 10/7 提案里**预埋上述裁剪梯**，结题=提案承诺，消除过度承诺扣分。
理由：保标题的曲线（接受率/净加速 × 2/4/8K + fp8 KV 延长区间）与复现协议**才是评分主体**；双 kernel 是 systems 加分，在 solo+零 CUDA+Windows 下是"用最高风险换加分"。

**评级：Go-with-cuts（有条件放行，高风险项显式条件化）。**
- 若按裁剪包执行：R≈205–215h，落在预算内，余量 ≈0–25h → **可行**。
- 若按 v4 字面全 MUST + 顺手碰 SHOULD：R≈267h+ → **约 35–45% 概率 11/25 前交不齐合规交付物或砍报告打磨** → 落到 High-risk。

## 5. 缓冲检查：裁剪后余量花在哪

裁剪后 R 档余量 **≈10–25h（对 220h 预算）**。优先级：
1. **干净环境一键复跑 + 复现审计**（4–6h）——run_id 哈希链/只追加 jsonl 若在第二台机器上跑不通，评分金矿变负分；先花。
2. **把 ppl/质量证据做厚一档**（4–6h）：一个固定长度档 × 各量化档的完整表，胜过临时补。
3. **K1 或动态树消融**（≤10h）——二选一，别两个都开。
4. 明确**不做**：int4 KV、0.2B 训练头、Triton 平行轨、gpt-fast 硬磕。
